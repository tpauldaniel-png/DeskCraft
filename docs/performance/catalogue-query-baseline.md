# DeskCraft catalogue query baseline - Day 61

Measured: 15 October 2026. Status: query-plan measurements captured; repository cleanup, metadata completion, and commit remain developer actions.

## Purpose and scope

Record the existing public catalogue SQL performance before Day 62 index work and Days 63-65 Redis caching. These are local development measurements from user-supplied PostgreSQL EXPLAIN exports, not a load test, API latency benchmark, scalability result, or production service-level target. No indexes or query optimizations were applied by the assistant while producing this document.

The report covers 11 SQL cases with four captured runs each (44 plans). The introductory simple product SELECT exercise is excluded. Product list and count are separate SQL statements. Product detail uses separate product, active-variant, and batch-image statements.

## Measurement method

- Run `EXPLAIN (ANALYZE, BUFFERS)` on the SQL generated by the existing SQLAlchemy repository.
- Keep the first captured execution separately. This is not a guaranteed cold-cache run; the plans already report shared-buffer hits.
- Report medians of the three subsequent executions, calculating planning and execution medians independently. Their medians need not come from the same run.
- The samples are small and were gathered manually at different times. Treat timing differences cautiously and repeat under comparable conditions after changes.
- No shared-block reads were reported in any of the 44 supplied plans. Buffer hits are accesses, not distinct blocks or product counts. Parent-node counts include descendants and must not be added together.
- EXPLAIN ANALYZE adds instrumentation overhead. Measurements exclude application processing, connection-pool waits, response serialization and network/UI time. Do not add independent medians and label the result endpoint latency.

## Findings tied to the captured plans

1. **Catalogue image lookup repeats per returned product.** The default list image subplan runs 12 times, search 5, category 3, and price 7. Each uses a sequential image-table scan followed by ordered selection of one image. Repeated-run image-subplan hits are 48, 20, 12, and 28 respectively. Investigate access paths as the catalogue grows; this does not establish a current production bottleneck or prove no image index exists.
2. **Variant ranking reads the active variant set.** The list scenarios scan 17 active variants and choose 12 first-ranked rows. Search and category filters do not restrict that underlying variant scan in these plans. Their upper ranking/sort branch is revisited, but the underlying variant scan has loops=1. The default case materializes the selected variant rows for reuse.
3. **Price filtering preserves starting-price semantics.** PostgreSQL selects the cheapest active variant per product, then filters ranked rows with inclusive bounds 0-10000, retaining 7 and removing 5. The outer list sort uses ranked price and product_id. The price predicates reject NULL prices, allowing an inner-join execution strategy for this case. Moving the minimum-price condition into the variant ranking input could change behavior and must not be done without reviewing semantics.
4. **Category filtering uses an existing index.** Both category plans use `ix_products_category_id` and `categories_pkey`. Product activity is checked as a residual filter after category lookup. No duplicate category index should be added merely because indexing is scheduled for Day 62.
5. **Detail lookups use existing indexes.** The product slug lookup uses `ix_products_slug`, joined to `categories_pkey`; variant retrieval uses `ix_variants_product_id` and sorts the two returned rows by price and ID.
6. **Detail images are retrieved in a batch.** One image statement uses the two variant IDs through an ANY/array condition (the planned form of this IN predicate). It scans once, keeps 6 images, rejects 49, and sorts the batch. It is not one detail-image SQL statement per variant.
7. **Counts still rank and join variants.** Without price filters, consider a conditional count-query path that omits variant work while preserving existing public visibility and product inclusion rules. Price-filtered counts need the starting-price logic. This is a candidate query change, not an implemented optimization.
8. **Search uses a product sequential scan.** The condition appears as `name ~~* '%%desk%%'`, with 5 passing and 7 rejected. `~~*` represents ILIKE. Doubled percent signs arise from the SQL rendering; adjacent percent wildcards have the same matching effect here. A trigram access path may be worth investigating on Day 62; a generic name index should not be assumed sufficient for substring search.
9. **Estimates differ from actual rows.** Examples include category scan estimate 130 vs actual 4, variants estimate 55 vs actual 17, and several one-row join estimates vs larger actual outputs. Inspect statistics and existing indexes before attributing every plan choice to a missing index. Refreshing statistics would change the experimental state; retain this baseline first.
10. **The results are small-data measurements.** Sequential scans and small in-memory sorts can be appropriate. Stable plan structure and buffer counts coexist with timing variability. None of these results establishes concurrent-user capacity.

- Inventory full index definitions and extensions before creating anything; avoid duplicates.
- Evaluate image lookup/filter/order access paths for both list thumbnails and batch detail images.
- Evaluate active-variant ranking access paths using product_id, price, and variant_id. Consider the activity predicate and the actual query shapes.

- Compare equivalent cases on the same data after any change. Preserve cheapest-variant and image-order tie-breakers, active product/category visibility, Decimal price handling, and correct pagination totals.
